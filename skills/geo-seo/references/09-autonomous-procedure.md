# 09. Complete autonomous procedure

Procedure an agent follows, end to end, to rebuild the search presence (Google, Bing, AI assistants)
of a site it is given. It is drawn from the jam-jam.org campaign (October 2026), whose plan v2 takes
precedence over plan v1. Each phase gives: inputs, work, outputs, success criteria, human checkpoints
and sub-agent routing.

The technical mechanisms cited (trailing slash, sitemap, robots.txt, JSON-LD, `llms.txt`, IndexNow) are
detailed in `03-technical.md`; the audit in `02-audit-method.md`.

Autonomy principle: continue until the success criteria; ask a question only if a decision is
structurally undecidable without the human. The checkpoints in this file are real decisions (legal,
personal account, publication), not comfort confirmations.

## Overview

| Phase | Name | Main deliverable | Agents |
|---|---|---|---|
| 0 | Scoping | "Scoping" section of `ETAT.md` | the main agent |
| 1 | Research | `RECHERCHE.md` | analysis (judgement), scouting |
| 2 | Measured audit | `AUDIT.md`, query sheets | low-cost scouting, analysis |
| 3 | Prioritised plan, reviewed, plan v2 | `PLAN.md` (v2) | architect, two reviewers |
| 4 | Implementation batches A to I | PR per batch, code and content | implementation, translation, review |
| 5 | Integrated visual QA | screenshots, measurements, fixes | visual QA |
| 6 | Deployment, verification, submission | release online, submissions | main agent |
| 7 | Record-keeping | `ETAT.md`, list of URLs | main agent |
| 8 | Follow-up at 2-4 weeks | tracking report | analysis |

Working folder: `handoff/<CAMPAGNE>/` in the site's repository, with `RECHERCHE.md`, `AUDIT.md`,
`PLAN.md`, `ETAT.md`, `HORS-SITE.md`, `PANEL.md`, `requetes/<langue>.md`, `captures/`. Progress lives in
`ETAT.md`: it is the current truth, read first at each resumption.

## Phase 0. Scoping

**Inputs**: the site's address, the repository, the brief (goal, languages, constraints).

**Work**:

1. **Scope.** Page families (home, tools, products, blog, legal, pages generated by an application),
   pages out of scope (pages belonging to another workstream: in the campaign, the conversion pages
   belonged to another workstream; the campaign only touched their sitemap and discovery metadata,
   after notifying the session concerned).
2. **Languages.** Exact list of languages, root language, languages without legal text (see
   `05-multilingual.md`).
3. **Access** (list to draw up and test BEFORE planning):

| Access | Useful for | If missing |
|---|---|---|
| Write access to the site repository (branches, PRs) | everything | stop |
| Official deployment procedure and script | phase 6 | stop |
| Search Console (domain property, service account) | audit, submission, tracking | audit without measurement: ask |
| Bing Webmaster Tools, IndexNow key | Bing submission | IndexNow only |
| Server access logs | AI bot visits | say so in the audit |
| Application analytics | the "ia" channel | measurement by the panel only |
| Personal accounts (directories, YouTube, Reddit, Wikidata, stores) | batch I | prepare only |

4. **Legal and brand constraints**: privacy policy (what may be collected), terms of use (CGU),
   comparative advertising, copyright (no song lyrics, no protected content), mandatory notices,
   validated figures (single table), banned wording, informal or formal address (tu / vous), use of the
   term « IA » (French for AI), typographic rules (no em dash).
5. **Technical constraints**: strict CSP (no inline script or style), static site or not, build tools,
   single deployment procedure, performance budgets.
6. **Coordination**: workstreams in progress by other people or sessions, sensitive files, locks,
   declaration of the workstream in the planned register (in the campaign: an external workstream
   identifier declared in the coordination file).
7. **Dedicated worktree**: work in a separate working tree, not in the shared tree; check that it is up
   to date with the main branch.

**Outputs**: "Scoping" section in `ETAT.md` (scope, languages, tested access, constraints, neighbouring
workstreams).

**Success criteria**: each access is tested with a real command (not assumed); the list of languages and
the scope are written down.

**Human checkpoint**: essential access missing; uncertain legal scope (what may be collected, compared,
published); contradictory brief. Do NOT stop for style, batch order or tool choice.

**Routing**: the main agent; low-cost scouting may test the access.

## Phase 1. Research

**Inputs**: the brief, any source given by the human (a video, an article), the web.

**Work**: establish what really works, by checking claims against primary sources. In the campaign, the
source was a marketing video: its claims were checked against published research (Princeton GEO study,
Ahrefs and Semrush studies, Google and OpenAI documentation). Each claim receives a verdict: **proven**
(official documentation or controlled study), **probable** (converging correlations), **overrated** or
**folklore**.

Expected content of `RECHERCHE.md`:

1. Table "claim / verdict / comment".
2. The mechanisms in plain terms: three recommendation paths (model memory, live search, entity) and the
   technical constraint (no AI robot executes JavaScript: only static HTML counts).
3. Levers retained, ranked by impact and cost.
4. "Do not do" (hidden text, mass pages, tampered dates, fake reviews, unofficial API).
5. Sources with addresses.

**Outputs**: `RECHERCHE.md` (one to two pages). **Criteria**: no claim without a verdict; sources are
dated; folklore is named as such.

**Human checkpoint**: none, unless a paid or private source is needed.

**Routing**: an analysis agent (judgement) for the synthesis; low-cost scouting to gather the sources.

## Phase 2. Measured audit

**Inputs**: the live site and its build, Search Console, `RECHERCHE.md`.

**Work**: measure, don't assume. Four measurements:

1. **Build inventory**: a script that produces one row per HTML page (model: `geo-inventory.py`, run with
   `python3 -I` on an untrusted build folder) with title and length, description and length, h1,
   canonical, robots, hreflang, JSON-LD types, presence of `sameAs` and of the logo, dates, word count,
   internal links, foreign words on non-native pages, presence of a table and of a visible date.
2. **Internal links**: redirect rate (links without a slash, to redirected pages).
3. **Search Console over 90 days**: clicks, impressions, CTR, position, per language and per page, plus
   queries per page (see `07-measurement.md`).
4. **Real requests** with AI robot user-agents: robots.txt, sitemap, `llms.txt`, public pages (200 or not).

**Outputs**: `AUDIT.md` with: inventory of pages by family; "what we do well"; "what we do badly" ranked
by severity (technical, entity, content, off-site); key Search Console measurements. Example of campaign
measurements: 972 indexable pages, 44% of internal links redirected, 0 sitemaps with `lastmod`, 547
descriptions too long, `Organization` without `sameAs`, 3 external mentions, brand at 72 impressions over
90 days. Query sheets `requetes/<langue>.md` (totals, per-page view, top 40, summary by theme, pages with
100 impressions and CTR under 1%).

**Criteria**: each defect has a number and a way to re-measure it; defects are ranked; each language has
its query sheet.

**Human checkpoint**: discovery of a legal breach (a published text contrary to law or to policy):
escalate.

**Routing**: low-cost scouting for the inventory and HTTP requests (mechanical, fully specified task);
analysis to rank the defects and read Search Console.

## Phase 3. Prioritised plan, reviewed by two experts, plan v2

**Inputs**: `RECHERCHE.md`, `AUDIT.md`.

**Work**:

1. **Plan v1**: cross-cutting rules (validated figures, checking in the code, no protected content, no
   em dash, CSP, translation pipeline, one agent per file, deployment through the official script, QA
   before merge), then batches A to I (phase 4), the execution order, the measurable success criteria.
2. **Review by two independent experts, read-only**:
   - an **AI / GEO marketing** expert: arbitrates the content (which pages to keep, merge, remove; what
     falls under folklore);
   - a **domain expert for the site** (in the campaign: music tools): checks the accuracy of each promise
     against the code.
3. **Plan v2**: a "Revision" section that groups the trade-offs and TAKES PRECEDENCE over the batches
   when it contradicts them.

Examples of what the reviews changed in the campaign:

| Reviewer | Decision |
|---|---|
| Domain | "Vingt instruments" (twenty instruments) is wrong, it is 21; "pentatoniques" (pentatonic scales, plural) is wrong, there is only one; the H/B notation is not displayed in the tool; the bass has no 6 strings; photo import is not reserved to mobile; chord progressions have no web tool |
| AI marketing | keep `/clavier-midi` (one URL per intent); remove `/progressions-accords` as a tool page (replaced by an article); merge three tuning articles into the existing tuner pages; cut the glossary to about 20 in-depth terms; postpone the "alternatives to X" pages (legal risk); abandon the Google Indexing API; "In brief" blocks with data specific to each page |

**Outputs**: `PLAN.md` v2. **Criteria**: each batch has an objective, files and an exit check; the success
criteria are quantified (0 links without a slash, 100% of URLs with `lastmod`, `Organization` with `sameAs`
on 100% of indexable pages, "In brief" block on 100% of tools, descriptions of 160 characters at most, 7
pages and 10 articles in the 10 languages, QA at 5 widths, sitemaps submitted); the trade-offs are readable.

**Human checkpoint**: legal decisions (comparison, data collection, retention); brand trade-off that
contradicts the brief; anything that commits a budget.

**Routing**: architecture agent (high judgement) for the plan; two review agents (analysis, read-only),
launched IN PARALLEL with the same plan and distinct instructions.

## Phase 4. Implementation batches

One branch and one PR per batch; delegated work always goes through a PR in a dedicated worktree; the
coordinator reads the actual diff and merges (an agent never merges its own PR). Increment the site
version at each batch. Before pushing: `build && push`. Keep `ETAT.md` up to date at the end of each batch.

### Order

1. Batch A alone, first (it touches the links, the sitemap and the template of all pages).
2. In parallel: fr/en writing of batches B, C, D in separate files; batch F (measurement).
3. Batch E (translations) once B, C, D are frozen.
4. Batches G, H, I after deployment or in parallel depending on dependencies.

### Batch table

| Batch | Content | Campaign example | Exit checks |
|---|---|---|---|
| A. Technical | trailing slash everywhere (single helper), sitemap with real `lastmod` and all sitemaps declared, JSON-LD entity graph (`Organization`, `WebSite`, `WebPage`, founder `Person`, software), metadata (canonical, unique titles, lengths), robots.txt (AI robots, sitemap `Allow`), `llms.txt` generated at build, versioned inventory | PR #60 | `check-trailing-slash`, `page-dates-check`, `check-seo-meta`, `geo-inventory.py`, build |
| B. Existing pages | "In brief" block of 40 to 60 words with figures specific to the page, reference tables generated from the code, "How to", FAQ, visible date and publisher, titles and descriptions rewritten for queries at positions 5 to 20, internal linking | PR #64: 31 pages fr/en | `check-marketing-numbers`, `check-seo-meta`, `check-em-dash`, check against the code |
| C. Need pages | one page per uncovered need, same template (H1 = need, In brief, steps, verified differences, FAQ, call to the application), plus "About" and glossary | PR #63: 6 pages | same, plus one URL per intent, no song lyrics |
| D. Reference articles | citable articles: direct answer at the top, self-contained sections, table, FAQ, link to the tool | PR #62: 6 articles | same, plus `check-inline-style` |
| E. Translations | one agent per language, one PR per language, blocking checks (see `05-multilingual.md`) | PR #65 to #73 | `i18n-assemble`, parity, labels, `check-seo-meta --strict` |
| F. Measurement | "AI assistants" channel in attribution, question panel, automated Search Console export | site PR #61 and application PR #782 | unit tests of the attribution; review of the policy |
| G. Submission | script sending sitemaps through the Search Console API, IndexNow extended to all sitemaps | batch G commit | run in `--dry-run` then for real |
| H. Store listings | re-read each listing against the brief (figures, missing needs), publish the text only | application PR #783: 38 Google Play listings | no binary; production publication: human checkpoint |
| I. Off-site | `HORS-SITE.md`: texts ready to paste, never executed by the agent | see `06-off-site.md` | accuracy review |

### Cross-cutting rules for each batch

1. Every function claim is checked in the code before being written; the platform is stated (web,
   Android, iOS beta, mobile only).
2. Figures only from the validated table; automatic check green.
3. No song lyrics or protected excerpts; generic or public-domain examples.
4. No hidden text, no instructions addressed to AIs in the pages.
5. No `<style>` or inline script (CSP).
6. Visible dates and `lastmod` follow the visible text (see `08-pitfalls-and-incidents.md`, B3).
7. Pages of another workstream are not touched.

### Structure of a batch PR

- Title: `<CAMPAIGN> batch X: <summary>`.
- Body: list of files, what the batch changes, checks run with their result (exit codes), open questions.
- Acceptance criteria verified by the coordinator, not by the author.
- No mention of an AI tool in commit messages or published PRs.

### Standard brief for an implementation sub-agent

```
Objective: <batch X, in one sentence>.
Files to write: <list>. Forbidden files: <list, including shared registers>.
Sources: <fr/en content files, AUDIT.md, PLAN.md batch X section>.
Rules: <cross-cutting rules above, informal address (tu), validated figures>.
Checks to run and pass: <list of scripts>; require the exit code, not the summary.
Deliverable: branch + PR; short report (changes, checks, unresolved points).
Forbidden: no merge, no deployment, no write to the production database.
```

**Human checkpoint during phase 4**: any change to a legal text (the repository's legal protocol before
touching it); any new data collection; publication in production of a store listing; any account to create.

**Routing**: architect for the new-page template and the key schema; implementation (medium effort) for A
to D and F; translation (one agent per language) for E; independent review (read-only) on each PR of A, F
and H and on a sample of E. A "mechanical" agent receives only fully specified tasks; a design task fails
with it.

## Phase 5. Integrated visual QA on the final build

Campaign decision: ONE integrated pass on the final build before deployment (nothing goes to production
without the deployment script), rather than a QA per batch; then a targeted counter-QA on the fixes.

**Inputs**: the final build (all batches merged), the list of pages (new, enriched, a sample per family and
per language).

**Work** (Playwright, headless browser, under the production CSP):

1. **Programmatic pass on all pages** (campaign: 732 pages at 400 and 1280 px):
   - horizontal overflow (`scrollWidth` = `clientWidth`);
   - no raw translation key displayed;
   - no broken image;
   - console errors and CSP violations.
2. **Visual pass on a sample**: 10 representative pages x 5 widths (400, 768, 1024, 1280, 1920 px) x 2
   themes (light and dark), full-page screenshots, which the QA agent READS (an unread screenshot proves
   nothing).
3. **Measurements**: CLS (threshold 0.1), transferred weight, animation stop button, decorative elements
   hidden from screen readers (see `check-vitrine-qa.mjs`).
4. **Points to look at**: scrolling tables (scroll cue), aligned cards, labels that do not fall at a line
   end, CJK fonts, interface screenshots in the right language, sharp and flat signs, button arrows.
5. **Fixes** by an implementation agent, new version; **targeted counter-QA** on the corrected pages only.

**Outputs**: folders `captures/qa-finale/` and `captures/qa-correctifs/`; list of defects and their status
in `ETAT.md` (fixed, known non-blocking remainders).

**Criteria**: 0 overflow, 0 raw key, 0 broken image on the programmatic pass; each major visual defect fixed
or recorded with a reason.

**Human checkpoint**: none, except a defect requiring a brand decision (an account name visible on a
screenshot, for example).

**Routing**: visual QA agent at medium effort at minimum (visual reading is not delegated to a cheap agent);
report only (no fix by the same agent).

## Phase 6. Deployment, online verification, submission

**Inputs**: main branch up to date and green, local build passing.

**Work**:

1. **Deploy through the official script only** (builds in a timestamped release, runs the checks, switches
   atomically). Never a manual build or copy to production.
2. **Blocking checks of the script** (campaign): em dash, developer page endpoints, inline styles, trailing
   slash, page dates, SEO metadata in `--strict`, quality measured in the browser (console, overflow,
   weight, CLS).
3. **ONLINE verification with AI-robot user-agents** (and not just a browser):

```sh
for UA in "Googlebot" "Bingbot" "GPTBot" "OAI-SearchBot" "ChatGPT-User" "ClaudeBot" "PerplexityBot"; do
  for URL in "https://[DOMAINE]/robots.txt" "https://[DOMAINE]/sitemap-index.xml" \
             "https://[DOMAINE]/llms.txt" "https://[DOMAINE]/[NOUVELLE-PAGE]/"; do
    printf '%s %s ' "$UA" "$URL"
    curl -s -o /dev/null -w '%{http_code} %{content_type}\n' -A "$UA" "$URL"
  done
done
```

   Expected: 200 everywhere, `llms.txt` as `text/plain`, `robots.txt` identical to the one in the repository
   (if a CDN sits in front of the site, check that it does not rewrite it), new pages at 200, `sameAs`
   present in the JSON-LD, declared sitemaps answer 200 to robots. In the campaign this check found the 403
   on the conversions sitemap (`08`, B6).
4. **Submission** for ALL languages:
   - sitemaps to Search Console through the API (`sitemap-index.xml` and each separate sitemap), then read
     the status: 0 errors, last crawl;
   - IndexNow for all sitemap URLs (campaign: 1,090 URLs accepted, code 200): Bing, Yandex, Naver, Seznam;
   - Bing Webmaster Tools: verify the property and the index;
   - NOT the Google Indexing API.
5. **Count by language** that the submitted URLs cover all languages (campaign: 560 URLs dated the same
   day, present in the 10 languages); a per-language count in `ETAT.md`.

**Outputs**: release online, deployment log (release identifier, number of URLs), status of submissions.

**Criteria**: all checks green; robots check with no 403 or 5xx; submissions accepted.

**Human checkpoint**: a publication on a store in production; a change to the server or CDN configuration
that goes beyond the repository (the campaign opened a ticket for the server exception and did it with the
neighbouring workstream).

**Routing**: main agent; low-cost scouting for the HTTP verification loop.

## Phase 7. Record-keeping

**Work**: keep `ETAT.md` as a current truth, not a log. Sections used in the campaign:

1. **Done**: batch by batch, with PR, figures and decisions.
2. **Known remainders** (minor, non-blocking).
3. **Decisions** (Indexing API abandoned, AI channel with no new enumerated value, integrated QA).
4. **Open questions for the human** (legal file, comparative pages).
5. **Deployment**: release identifier, check results, submissions, online verification.
6. **URLs created or modified**: list per page, with "NEW" or "modified", the number of languages ("10
   languages"), the `lastmod` date.
7. **Follow-up**: dated later events (server fixes, legal texts, screenshots).

Other lasting outputs: a project memory note (added mechanisms to respect in any future batch, remainders
for the human); a line in the human's queue for the batch I actions; follow-up tasks scheduled in the
project's management tool (no scheduling in a temporary session folder: it disappears).

**Criteria**: an agent resuming the work understands the state by reading `ETAT.md` alone.

## Phase 8. Follow-up at 2-4 weeks

**Inputs**: the deployment of day D, the submissions, the baseline.

**Work**: see `07-measurement.md` (cadence, panel, indicators).

1. **Weeks 2 to 4**: first panel log (baseline), Search Console comparison against the starting point over
   28 then 90 days, sitemap status, indexed pages.
2. **One-page report**: summary, GSC per language, winning and losing pages, proposed title rewrites for
   queries at positions 5 to 20 with low CTR, panel, "ia" channel, off-site, questions for the human.
3. **Fixes**: titles and descriptions of low-CTR pages (new short batch, same checks), accuracy fixes
   flagged by the panel.
4. **Plan target**: at 4 to 8 weeks, niche-query CTR above 3% and average positions rising; mentions in
   assistants in months.

**Human checkpoint**: persistent inaccurate mentions in an assistant (fixing at the source = often an
external listing maintained through a personal account); decision to extend off-site work.

**Routing**: analysis (medium effort) for the report; low-cost scouting for the data export; the panel
itself is done by a human with their accounts.

## Summary: when to stop and ask the human

| Situation | Why | What the agent prepares |
|---|---|---|
| Legal decision (legal text, data collection, retention, comparative advertising, copyright) | binds the publisher; a defect is a breach, not a typo | precise question, options, proposed text, translation at parity |
| Creating or using a personal account (directories, YouTube, Reddit, Wikidata, Product Hunt) | only the human can act under their own name; fake accounts forbidden | texts ready to paste, execution order, a line in their queue |
| Publication in production on a store (Google Play, App Store) | irreversible, written approval required | listings written, checked, submitted as drafts or internal tests |
| Missing access (Search Console, deployment, logs) | cannot measure or publish | list of accesses with the test command |
| Infrastructure change outside the repository (server, CDN, firewall) | outside the repository's scope, incident risk | configuration block ready and tested locally |
| Product trade-off (function promised but missing, e.g. H/B notation) | product decision | product ticket, content that does not promise the function |
| Contradiction between the brief and the product's actual state | risk of false content | list of gaps with proof in the code |

## Summary: sub-agent routing

| Need | Agent class | Effort | Remark |
|---|---|---|---|
| Inventories, HTTP requests, counts, access tests | scouting / mechanical execution | low | fully specified tasks only |
| Research synthesis, Search Console diagnosis, tracking report | analysis | medium | read-only |
| Plan, key schema, cross-system trade-offs, stubborn problem | architect | high | read-only; never the maximum level |
| Batch implementation, translation (one agent per language), fixes | implementation | medium | one agent per file, one PR per batch |
| Independent review (accuracy, privacy, actual diff) | review | medium | read-only, two reviewers with different profiles for the plan |
| Visual QA (screenshots read, measurements) | visual QA | medium at minimum | report only |

Delegation rules: a precise objective, a limited scope, a short deliverable; do not create an agent when a
simple task can be done directly; launch agents in parallel only for independent work (distinct files);
raise effort one notch only after an observed failure, not as a precaution.

## Procedural mistakes to avoid

1. Planning before measuring (half of the campaign's defects were only visible through measurement).
2. Writing content without checking it in the code.
3. Translating before freezing the source.
4. Doing QA batch by batch instead of an integrated final pass, then forgetting the counter-QA.
5. Deploying without checking with AI-robot user-agents.
6. Submitting only English.
7. Forgetting to record: resuming after an interruption depends on `ETAT.md`.
8. Promising results in days: indexing takes days to weeks, assistant mentions take months.
